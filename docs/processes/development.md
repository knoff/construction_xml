# Процессы разработки

## Общие принципы

1. **Фичевая изоляция.** Каждое изменение локализовано в своей области: backend/ frontend/инфраструктура.
2. **Документация в коде.** При рефакторинге и новых фичах обновляем разделы в `docs/`.
3. **Единый стиль.** Следуем линтерам и форматтерам (Python — `black`, TypeScript — `eslint`/`prettier`).
4. **Обратная совместимость.** Изменения API согласуем с фронтом, поддерживаем переходный период.

## Жизненный цикл задачи

1. **Планирование**
   - Создать issue или описание задачи.
   - Определить затронутые слои и необходимые изменения в документации.

2. **Разработка**
   - Вести работу в ветке `feature/*` или `refactor/*`.
   - Писать тесты параллельно с кодом.
   - Обновлять документацию при изменении архитектуры или контрактов.

3. **Code Review**
   - Проверять соответствие требованиям, структуре, тестовому покрытию.
   - Чеклист PR: описание, тесты (и результаты), обновление docs, миграции.

4. **Merge & Deploy**
   - После одобрения запускается CI.
   - При необходимости выполняем ручные шаги деплоя (описаны в `docs/architecture/infrastructure.md`).

## Шаблоны

- **Backend сервис** — создаётся в `app/services/domain/<module>/service.py`, `__init__.py` экспортирует класс сервиса и исключения.
- **API роут** — добавляется в `app/api/http/<module>/router.py`, регистрируется в `app/api/routes`.
- **Frontend фича** — структура `features/<feature>/{components,api,store,types}`.

## Правила для `_tmp` и legacy

- Временные файлы хранятся в `app/_tmp` и сопровождаются пометкой в документации.
- На любую legacy-реализацию должен быть план миграции.

## Автоматизация

- CI проверяет форматирование, линтинг, тесты backend/frontend.
- Перед merge обязательно `pre-commit` (добавить конфигурацию) и локальный запуск тестов.
