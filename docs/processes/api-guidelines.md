# Руководство по API

## Цели

- Единообразие контрактов между backend и frontend.
- Прозрачность для интеграций и автоматической генерации клиентов.
- Упрощение тестирования и эволюции API.

## Общие правила

1. **Версионирование.** Новые критичные изменения вводим через префиксы (`/api/v2/...`) или feature-флаги. Legacy оставляем в `legacy.py`.
2. **Единый формат ответов.**
   - Коллекции возвращаем массивами; объекты — словарями.
   - Если нужны метаданные, используем обёртку `{ "data": [...], "meta": {...} }`.
   - Исключаем ситуации, когда часть ответов имеет поле `items`, а часть — нет.
3. **Контекст.** В ответах сложных эндпоинтов используем поле `context`, содержащее идентификаторы и описания сущностей.
4. **Фильтры и пагинация.**
   - Параметры query пишем в snake_case.
   - Пагинация: `limit`, `offset` или `page`, `page_size`. Ответ содержит `meta.total`.
5. **Ошибки.**
   - Формат: `{ "detail": "message" }` или `{ "detail": { "code": "...", "message": "..." } }`.
   - Для валидационных ошибок используем `422` с подробностями полей.
6. **Документация.**
   - Обновляем OpenAPI и раздел `docs/processes/api-guidelines.md` при добавлении/изменении эндпоинтов.
   - Примеры ответов (JSON) приводим в docstring и в документации.
7. **Тесты.**
   - Контрактные тесты фиксируют формат ответов и заголовков.
   - Изменения в API сопровождаются обновлением тестов и фронтенд-адаптеров.

## Структура эндпоинтов

- `/api/<resource>` — CRUD операции.
- `/api/<resource>/<id>/<subresource>` — вложенные ресурсы.
- `/api/value-links/structures/...` — пример специализированных эндпоинтов (обязательно описываем контекст и `matches`).

## Ограничения и best practices

- Не прокидывать непосредственно модели ORM в ответы.
- Не смешивать синхронные и асинхронные обработчики в одном модуле.
- Локализация — на фронте (backend отдаёт коды и ключи при необходимости).
