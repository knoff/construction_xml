# Тестирование backend

## Цели

- Проверка бизнес-логики доменных сервисов.
- Гарантия корректности инфраструктурных адаптеров (БД, MinIO).
- Валидация API-слоя и контрактов ответов.

## Типы тестов

1. **Unit**
   - Расположение: `tests/backend/unit/`.
   - Покрывают функции и методы доменных сервисов без обращения к внешним ресурсам.
   - Используют моки для инфраструктуры (`pytest-mock`).

2. **Интеграционные**
   - Расположение: `tests/backend/integration/`.
   - Запускают FastAPI-приложение через `TestClient`.
   - Используют тестовую БД (PostgreSQL) и фикстуры данных.
   - Проверяют ответы эндпоинтов, соответствие JSON-схемам.

3. **Контрактные/снапшот**
   - Проверяют стабильность формата ответов.
   - Снапшоты хранятся рядом с тестами (`*.snapshot.json`).
   - Любое изменение требует осознанного обновления снапшота.

## Организация

- Конфигурация `pytest.ini` содержит общие настройки.
- Общие фикстуры: `tests/backend/conftest.py` (инициализация приложения, сессии БД).
- Используем фабрики (например, `factory_boy`) для сущностей.

## Работа с БД

- Для юнит-тестов БД мокируется.
- Интеграционные тесты используют отдельную базу/схему, которая очищается перед каждым тестом.
- Миграции применяются при старте тестового окружения (`alembic upgrade head`).

## Работа с MinIO

- Локальный MinIO поднимается в Docker Compose (`tests/docker-compose.yml`).
- Для ускорения можно использовать фейковые драйверы или tmpdir.

## Инструменты

- `pytest`
- `pytest-asyncio` (если есть async-функции)
- `pytest-mock`
- `httpx`/`starlette` TestClient

## Требования к PR

- Любое изменение backend-сервисов сопровождается юнит-тестом.
- Изменение API — обновлением интеграционного/контрактного теста.
- Покрытие новых модулей ≥80% (уточняется).

## Будущие шаги

- Автоматическое формирование отчётов покрытия (Codecov).
