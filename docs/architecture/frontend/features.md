# Архитектура фронтенд-фич

## Назначение документа

Этот документ описывает, как организуются фичи и подфичи (subfeatures) во фронтенде проекта. Здесь фиксируются слои, публичные интерфейсы и правила взаимодействия между подсистемами.

## Общие определения

- **Фича** — самостоятельная функциональная область пользовательского интерфейса. Фича владеет своими типами, состоянием и сервисами.
- **Подфича (subfeature)** — часть фичи, отвечающая за отдельный аспект функции (например, рендер форм, переопределения UI, валидатор). Подфичи могут иметь вложенность любой глубины.
- **Публичный API** — набор экспортов (`index.ts`) на каждом уровне, через который внешние модули могут использовать фичу или её подфичи.

## 2. Базовая структура фичи

```
features/<feature>/
  core/        – доменная логика, типы, утилиты без React и UI
  runtime/     – интеграция с приложением: провайдеры, glue-компоненты, хуки
  components/  – визуальные компоненты фичи
  api/                    # вызовы backend (опционально)
  modules/     – вложенные подфичи по этой же схеме
  hooks/       – публичные хуки фичи (опционально)
  index.ts     – фасад фичи, экспорт публичного API
```

> **Почему нет `shared/` и `api/`?**
> Ранее мы выделяли эти каталоги отдельно, но теперь договорились:
> * переиспользуемые UI и утилиты выносим либо в общую фичу, либо в самостоятельные модули;
> * сетевые вызовы считаем адаптерами и размещаем в `adapters/`, а чистые типы — в `core/`.
> Если потребуется вернуть отдельные каталоги, зафиксируем это отдельно.

Фича может опускать каталоги, которые ей не нужны. Важно, чтобы `index.ts` агрегировал публичные части как самой фичи, так и её подфич.

## 3. Структура подфич (modules)

Каждая подфича повторяет ту же структуру, что и сама фича:

```
modules/<subfeature>/
  core/
  runtime/
  components/
  adapters/
  modules/
  index.ts
```

> Для подфич действуют те же правила: `shared/` и `api/` не используем — вместо них задействуем `core/`, `adapters/` или выносим функциональность на уровень фичи.

### Слои подфичи

| Слой        | Ответственность | Примечания |
|-------------|-----------------|------------|
| `core/`     | Чистая логика, типы, state-машины. Не зависит от React. | Может включать утилиты, сервисы, модели. |
| `runtime/`  | Интеграция с React: провайдеры, контексты, хуки, менеджеры состояния. | Все зависимости на React и UI проходят здесь. |
| `components/` | Визуальные компоненты, не содержащие бизнес-логики. | Внутри допускается группировка по типам (поля, блоки, диалоги). |
| `adapters/` | Расширения и интеграции с другими подфичами или внешними системами. | Примеры: validator ↔ value-links, renderer ↔ mapper. |
| `modules/`  | Вложенные подфичи, повторяющие тот же шаблон. | Использовать, когда подфича становится слишком крупной. |

### Публичный API (`index.ts`)

- Экспортирует только те элементы, которые нужны внешним потребителям.
- Внутренние файлы импортируются внутри подфичи напрямую, но наружу доступны только через `index.ts`.
- При добавлении нового слоя/API обязательно обновлять `index.ts` и документацию.

## Взаимодействие между подфичами

1. **Через публичные API.** Любые зависимости между подфичами должны проходить через `modules/<subfeature>/index.ts`.
2. **Адаптеры вместо прямых импортов.** Если одна подфича расширяет другую, создаётся файл в `adapters/`, который подключается опционально.
3. **Минимальная связность.** Базовые слои не должны зависеть от специфичных компонентов других подфич. Например, `core/validator` может использовать сервисы `value-links` только через интерфейс, предоставленный адаптером.
4. **Провайдеры и контексты.** Общие провайдеры (например, состояние формы) размещаются в `runtime/` и реэкспортируются наружу, чтобы другие подфичи могли подключаться при необходимости.

## Пример: forms-renderer

Фича `forms-renderer` будет приведена к следующей структуре:

```
forms-renderer/
  index.ts
  core/
    types.ts
    utils/
  modules/
    renderer/
      index.ts
      core/
      runtime/
      components/
      adapters/
    ui-overrides/
      index.ts
      core/
      runtime/
      components/
        fields/
        blocks/
        dialogs/
      registry/
    mapper/
      index.ts
      core/
      components/
      api/
      adapters/
    validator/
      index.ts
      core/
      runtime/
      adapters/
    value-links/
      index.ts
      core/
      runtime/
      components/
```

- `renderer` отвечает за базовую отрисовку форм и предоставляет провайдеры состояния.
- `ui-overrides` расширяет визуальный вид блоков через собственный реестр компонентов.
- `validator` проверяет данные и предоставляет API для интеграции с `renderer` и `value-links`.
- `value-links` управляет привязками данных между полями.
- `mapper` реализует сопоставление значений (диалог, состояние, API).

Каждый модуль подключается к остальным через публичные API и адаптеры, что позволяет развивать подсистемы независимо.

## Рекомендации по развитию

1. **Планируйте границы.** Перед добавлением новой функциональности определите, это фича, подфича или расширение существующего модуля.
2. **Соблюдайте слои.** Не смешивайте UI и бизнес-логику. Вся логика должна быть в `core/`, UI — в `components/`.
3. **Документируйте API.** При изменении публичных экспортов обновляйте `index.ts` и документацию.
4. **Покрывайте тестами.** Логику в `core/` сопровождайте unit-тестами; сложные UI-компоненты — storybook/визуальными тестами.
5. **Используйте адаптеры.** Любые зависимости между подфичами оформляйте как адаптеры, чтобы избежать жёстких связей.
